# Changelog

## 2.2.0 (unreleased)

### Full CLI option parity

- Every option of every `abs` command that changes what is sent or returned is now an `execute_command` param. Examples: `getMetricResults` `cached` (previewer cache, `GET /experiments/{id}/metrics/main?use_cache=1`), `metricId`, `segment`, `filter`, `from`/`to`; the ~30 `listExperiments` filters; `search`/`sort`/`asc`/`desc`/`archived`/`ids` on the list commands whose CLI command takes them (`get_command_docs` lists each command's params); `show`/`exclude`/`showOnly`/`raw` on the get commands; `unarchive` on archive commands; the `metrics list` and `users list` client-side filters; flag-style fields, `note` and `dryRun` on `updateExperiment`; `templateContent`/`customFields`/`dryRun` on `restartExperiment`; `activate`/`newVersion` on `createMetric`; the `statistics power-matrix` flags; `bulk*` selection by `state`/`app` with `dryRun`.
- New commands for the CLI commands the MCP did not have: `experiments.createExperimentFromOptions`, `analyzeExperiment`, `watchExperimentTick`, `getExportStatus`, `findRecentExport`, `getMetricDeps`; `metrics.createMetricVersion`; `users.getUserApiKey`/`updateUserApiKey`; `auth.editProfile`; `exportconfigs.cancelExportHistory`; `datasources.previewDatasourceQuery`/`setDefaultDatasource`/`getDatasourceSchema`/`deleteDatasource` and the json-layouts commands; `events.getEventUnitData`/`deleteEventUnitData`/`getEventJsonValues`/`getEventJsonLayouts`/`getEventsSummary`; the `customfields` group.
- The catalog works across the whole `@absmartly/cli` peer range (`>=1.7.0 <2`): `scripts/peer-cli-check.ts` checks that a CLI install has every core function and APIClient method the catalog calls, and CI runs it on the peer minimum. Helpers older CLIs lack (`columnarToRows` before 1.12, the `listNotifications` limit before 1.17) are applied in this package.
- `tests/fixtures/cli-command-options.json` maps every CLI command and option to its command and param (generated by `npm run parity:cli`, checked by the unit tests).

### Raw API requests

- `api.rawRequest` is `abs api`: `path` (with an optional query), `method`, `query`, `body`, `headers`, sent through `APIClient.rawRequest` with the session's credentials. `GET` runs directly; `POST`, `PUT` and `DELETE` need confirmation. The path guard and `FetchHttpClient` keep requests under the API base. `endpoint-manifest.json` lists it as the one command with a runtime path (`dynamicApiMethods: ["rawRequest"]`).

### Behaviour changes

- Variant screenshot sources given to the MCP server (the `screenshot` param, and `![…](…)`/`screenshot:` in any `templateContent`, including `createExperimentFromTemplate`) must be `data:` URIs; existing uploads are referenced by `screenshotId`/`screenshot_id`. The server does not read file paths or fetch URLs: on a server those are the server's files and network, not the caller's (the CLI runs on the caller's machine, so it accepts both).
- `listMetrics` with client-side filters reports `scanIncomplete` and a warning when the scan stops at its page cap.
- `createMetric`/`createMetricVersion` with `activate`: if activation fails after creation, the result keeps the created ID with `activated: false` and a warning, instead of an error that hides the created metric.
- `updateExperiment` applies `screenshotId` and the other CLI-style fields (2.0.1 ignored every key but `changes`); an explicit `changes` field wins over a CLI-style field.
- `updateExperiment` with neither `changes` nor a field is an error (2.0.1 sent a PUT that changed nothing). A documented `dryRun: true` is never asked for confirmation.
- `getMetricResults` `metricId` is a documented ID: an invalid one is rejected before any request.
- `discover_commands` listings are also bounded by size, so a long entry (like `listExperiments`) cannot push a listing over the response limit.

## 2.1.0 (unreleased)

### Dependencies

- The `@absmartly/cli` devDependency is `1.17.1` (pinned exactly). Since 1.17.0, feature flags created from a template no longer get experiment-only analysis fields, which made test-1 return HTTP 500, and feature metrics are sent as guardrails, as in the UI. 1.17.1 only changes the CLI's own `users create/update --role`; the MCP user commands call the API client directly and are unaffected.

### Catalog contract

- 23 commands whose documented params did not match the CLI core now document what the core needs: `role` on access grant/revoke, `unitType` on `estimateParticipants`, `oldPassword`/`newPassword` on `resetMyPassword`, top-level filters on insights/activity/events, and more. `refreshFields` is removed. See the 2.1.0 PR for the full table.
- Params the core never reads are deprecated: still accepted, hidden from `get_command_docs`.

### Security

- `FetchHttpClient` only sends requests under `<base>/v1/` or the root `/auth/current-user` paths. Dot segments in any encoding, backslashes, encoded separators, control characters and `undefined`/`null`/`NaN` path segments are refused before `fetch`.
- ABsmartly endpoints are parsed by one function (`parseAbsmartlyEndpoint`) everywhere they enter: OAuth consent, API-key requests, the `/register` link, stored props and `FetchHttpClient`. An endpoint is parsed once where it enters; what is stored or passed on is its `apiUrl`, which parses back to the same endpoint, so a base path that itself ends in `/v1` (an API at `/tenant/v1/v1`) is kept through consent, the redirect and the callback. `ConsentOutcome` (approved) and `onApprove` also carry the parsed endpoint.
- Every argument an APIClient method puts into a request path is checked before the method runs, whichever route it came by (`withPathIdGuard`, applied once where this package creates its client and again in `executeCommand` for a host's own client). Path arguments come from `src/api-path-args.ts`, generated from the `@absmartly/cli` build and looked up by parameter name: an ID must be a positive integer, and a word (uploadFile's `usage`) must not contain `/ \ . % ? #`. `request`/`rawRequest` validate their path (leading `/`, no dot segment in any encoding, no backslash). Any method not in the table fails closed: non-primitive arguments, strings with path characters and numbers that are not positive integers are refused. The `absmartly://<entity>/{id}` resource templates get the same check.
- The path table is generated from `@absmartly/cli` `1.17.1`, the exact devDependency. The peer range is unchanged (`>=1.7.0 <2`). The installed version is checked at load. On any other version (or one that cannot be read) the guard logs one warning naming both versions and treats every method as unknown: strings with path characters and numbers that are not positive integers are refused, while plain-object and array arguments (bodies, options) pass. Leftover risk on such an install: a CLI method that builds a path from a field of an object argument is not checked. `request`/`rawRequest` are always checked. Install `1.17.1` for exact checks.

### Behaviour changes for direct executeCommand callers

`executeCommand` dispatches 2.0 core-shaped calls as 2.0.1 did. These are the intentional differences, each pinned by `npm run parity:main` (`scripts/parity-main.ts`, `EXPECTED_DIFFERENCES`):

- A path ID that is not a positive integer is an error: `goalId: "1/../users"`, `experimentId: null`, an ID nested in `data` (`{ data: { id: "abc" } }`), and a missing one (2.0.1 sent `/experiments/undefined`).
- `revokeExperimentAccessUser`/`Team` with `role`: the role is resolved to its asset role ID. 2.0.1 ignored `role` and sent `DELETE .../undefined`.
- `listCustomFields` without `type` defaults to `"test"` (2.0.1 filtered on `undefined` and always returned no fields).
- `generateTemplate` without `name`/`type` defaults to `"My Experiment"`/`"test"` (2.0.1 generated a template named `undefined`).
- `platformconfig.getPlatformConfig {id: null}` and `updatePlatformConfig {id, value}` fail as in 2.0.1, with a message naming the config problem.
- ID values are normalised to integers in request bodies and results too (`userIds: ["2"]` sends `user_ids: [2]`; `createAnnotation {experimentId: "5"}` sends `experiment_id: 5`).
- Datasource and storage tests: `datasourceId`/`configId` now test the saved config (2.0.1 ignored them and posted an empty body); `validateDatasourceQuery` with `datasourceId` requires `query`; a call with neither an ID nor `config` is an error.
- `grantExperimentAccessUser {roleId: "Editor"}`: `roleId` must be an asset role ID; pass a name in `role` (2.0.1 sent `asset_role_id: "Editor"`).
- Declared aliases that disagree with their documented param (`roleId` vs `role`/`assetRoleId`, `id` vs the documented ID) are an error; 2.0.1 silently picked one.
